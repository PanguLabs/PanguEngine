## 1. 意图、范围与完成标准

将隔离的 Attr / CodeGen 验证转成正式宿主工具：业务 Module 在普通 C++23 头文件中声明属性，PanguMetaTool 按真实目标配置校验并生成描述及强类型访问，生成结果编译进原 Module，由实际消费者操作真实对象。

首版同时自动生成原生 Query 导出包装和各 Host 的静态 Catalog。保留已有 C++ ModuleDefinition、Register 回调、注册事务及生命周期，不新建 Module 属性协议。

成功的最小闭环包含：一个实际 Module 的公开普通类型、无参数 Type 属性、多个不同类型的已标注字段、const 与 Private 字段；消费者枚举描述、通过强类型接口读取及修改合法字段，再由普通 C++ 检查修改结果。该路径在 Monolithic / Modular 下均通过，并验证动态库相关借用的关闭行为。

### 1.1 用户已经确认的选择

1. 正式工具及 CMake Target 为 `PanguMetaTool`，源码根为 `BuildTools/PanguMetaTool/`；生成根仍使用 `Generated/PanguMeta/`，元数据命名空间为 `pg::meta`；历史 PoC 名称和路径保留。
2. 首版采用“描述 + 强类型字段访问 + 真实 Module 消费”，以实际对象读写验收。
3. `pga::Type` 允许无参数；需要稳定身份时才显式提供 TypeId，不要求所有标注类型具有持久身份。
4. 字段默认使用名称，允许显式固定稳定键；数字 FieldId 不作为所有字段的必填要求。
5. 公共可写字段支持修改，const 字段只读；Private 字段首版保留描述，访问沿用原类型已有公开接口，不自动取得访问权限。
6. 保留 C++ ModuleDefinition 与 Register 回调；工具接管 Query 包装及 Host Catalog 生成，不生成整个 ModuleDefinition。
7. 一个 Engine 工作区对应一个当前 Game Project；切换 Project 时复用 Engine 构建目录，按新 Project 的配置更新并覆盖之前的生成与编译产物。同一 EngineBuildRoot 的 Configure/build/test 会话串行执行。
8. 现有内部 Meta 模型统一命名为 MetaIR，使用 C++23 强类型、拥有数据的内存表示，与 Clang AST 解耦；属性默认值、常量及语义约束在进入 CodeGen 前完成规范化。
9. `pg::meta` 定义统一的基础元数据语义及需要时可在 Runtime 消费的接口，包含 TypeInfo / FieldInfo 等轻量描述；`pg::meta::ir` 保存构建期专属信息，负责跨声明汇总、规范化和生成准备。两者共享语义契约，不要求相同对象布局。
10. 构建请求与类型语义分开；输出按实际消费者需要生成和保留。首版 MetaIR 仅存在于工具内存中，不增加 Meta 文件、Exporter 或磁盘交换协议。
11. 工具在宿主运行，目标 TypeInfo 由目标编译器编译生成；不把宿主对象内存、指针、布局或偏移直接保存为目标运行时结构。MetaIR 的目标相关事实须明确关联其适用的真实目标上下文。

2026-11-09 用户通过 grilling 确认了本文进一步收敛的范围与行为，完整决定索引见 §12。精确函数/文件名、请求字段拼写及具体实现策略由实施计划统一记录，不将尚未实现的接线描述成既有能力。

### 1.2 边界

本轮不交付通用动态对象读写、全局 Type Registry、Inspector、Serialization / SaveGame 格式、网络 Schema、自动 Getter/Setter 绑定、验证/通知/Undo、Private 无侵入访问、通用函数 Invoke 或脚本绑定。已有 Module / Scope / CodePin 契约继续约束所有真实对象与代码借用。

属性注册框架首版覆盖自有 Type / Field 与必要参数类型，允许随后在工具源码中扩展。外部游戏/Plugin 在不重编工具的前提下安装新属性，不在本轮范围；不新增动态属性插件。

## 2. 方案比较与选定路线

| 路线 | 作用与成本 | 结论 |
| --- | --- | --- |
| 仅生成名称、ID 和类型等描述 | 能迁移基础 PoC，但真实对象操作仍未贯通 | 作为比较方案，用户选择了下面的路线 |
| 描述与已知类型的强类型字段访问 | 可由普通 C++ 实际消费，编译器检查类型和 const；支持按需描述 | 用户选择，作为首版 |
| 动态类型查找与类型擦除读写 | 可服务调用点未知的类型，需要额外对象访问、转换和描述生命周期协议 | 后续由实际消费者需求驱动 |

工具继续采用独立 LibTooling 程序，在进程内装配 Attr 与 CodeGen。目标编译器编译原始源码和普通辅助代码，不加载工具插件，不使用替代源码视图。

## 3. 身份、命名与属性参数

### 3.1 类型身份

首版支持 `[[pga::Type]]` 和 `[[pga::Type("32 位小写十六进制非零 ID")]]`。两者均可按消费者请求生成强类型访问和描述；前者的稳定 TypeId 为空，后者额外携带稳定 TypeId。ID 与 ModuleId 是不同的强类型，不互换。

无 ID 类型依靠调用点已知的 C++ 类型及其生成特化使用。限定类型名用于显示、诊断和生成符号映射，不宣称重命名稳定；不得将类型名哈希、RTTI 地址或宿主地址升级为持久身份。编译期特化、运行期 RTTI 与持久 TypeId 各司其职。

同一受检 Module 的不同类型不得使用重复显式 ID；同一目标中重复包含同一声明应去重，而不是误报。独立模块的 ID 冲突只有在明确汇总这些模块的工具验收路径中才能检查，不声称扫描有限输入已保证整个进程唯一。首版不提供按 TypeId 查询对象的 Registry。

### 3.2 字段键

Field 采用无参数或一个类型化 Options 参数：`[[pga::Field]]`、`[[pga::Field(pg::meta::FieldOptions{.Key = "Health"})]]`。首版不增加位置字符串快捷形式或裸命名参数。

轻量 `FieldOptions` 首版仅含 Key 与 ReadOnly，建议具体声明为 `const char* Key{nullptr}` 和 `bool ReadOnly{false}`，按该顺序声明；精确成员布局不是 Frozen ABI。其公共头不依赖 Clang。Key 未指定时使用 C++ 字段名；指定时必须是可在构建期求值的非空 UTF-8 字符串，不能含内嵌零字符。同一类型的全部已标注字段（含 Private）键必须唯一。键按完整字节串比较；若内部使用哈希加速，还须处理碰撞，不能仅比较哈希。

Field 不接受历史 PoC 的必填整数 ID。旧小写属性及其临时参数不是正式兼容 API，迁移正式测试时须按新契约重写有效场景。

Key 用于区分描述中的字段，也可由后续持久化协议明确消费；本轮不因此交付存档兼容承诺。默认键随 C++ 字段改名而变化；需要保持键时显式填写旧键。字段移动、类型变化、删除后复用及迁移规则仍属于对应 Schema 设计。

ReadOnly 限制生成接口的写入能力，不改变原 C++ 成员本身。不能承诺阻止业务代码直接写 public 字段。只读状态由语言 const 和该选项共同决定。

### 3.3 参数校验与支持范围

Attr 统一执行数量、类型、常量求值、适用声明及重复规则检查；Options 默认值读取其 C++ 声明的语义，不能在处理器维护第二套默认值。拒绝未知属性、错误大小写、错误命名空间、重复属性、错误 Options 类型、运行期值及无合法消费者的选项。

Field 的所属类型必须标注 Type，允许无参数 Type；孤立 Field 明确报错，不隐式为任意类型启用反射。

当前 PoC 只验证了 bool/int 两成员 Options。本草案增加字符串键，须新增正式验证，不能直接沿用旧探针通过结论。字符串字面量、constexpr 别名、Options 聚合及 constexpr 工厂返回值按同一常量规则处理；无法可靠提取的形式明确诊断。

首版生成输入为可独立包含的头文件。支持有名称、完整定义的非模板 class/struct，以及其直接声明的普通非静态字段；字段类型由 AST 推导。const、别名、标量、枚举和普通对象字段纳入测试。基类可存在，但首版不隐式合并基类字段；基类自行声明与消费描述。

对已标注的位域、引用成员、static 成员、匿名类型、union、依赖模板或仅在业务 `.cpp` 定义的反射输入，首版应明确拒绝或在输入登记时拒绝；不能悄悄漏掉声明。未标注成员不进入字段集合，也不要求为其生成访问。

普通对象、指针、容器及数组字段仅描述和访问成员本身，不隐式展开嵌套类型、跟随指针或枚举元素。成员不能合法赋值时不生成写入入口；成员的只读借用不承诺整棵对象图深度不可变。

## 4. 工具组成与目标侧接口

### 4.1 工具内部

| 部件 | 责任 |
| --- | --- |
| Driver | 接收派生的生成请求、选择真实目标上下文、组织扫描/生成、收集诊断、发布产物 |
| 具体 TypeAttribute / FieldAttribute | 描述名称、参数、适用对象、重复与专属规则 |
| 参数绑定器与 Clang 适配器 | 共用基础检查、读取常量语义，并将结果交给具体规则 |
| MetaIR（`pg::meta::ir`） | 用拥有数据的纯 C++23 模型保存来源、归属、可选稳定身份、字段键和规范化语义，执行跨声明汇总与生成准备 |
| GenerationRequest | 保存任务种类、目标编译上下文、输入输出登记及 Module/Host 装配信息，不作为类型反射语义的一部分 |
| CodeGen | 按请求消费经检查的 MetaIR 或装配信息，生成实际消费者需要的 C++ 接口、实现及描述 |

属性定义、一次属性使用的数据与 Clang 注册对象分开。具体属性不要求公开继承 Clang；内部适配器满足 ParsedAttrInfo。所有处理器在首次解析前安装，按领域显式清单集中登记，不通过一个布尔模板或巨型 switch 区分全部属性。

MetaIR 是现有内部模型的正式名称，不新增重复中间层。建议由 `TypeDefinition`、`FieldDefinition`、`SourceLocation` 和 `Model` 等构建期类型组织数据；具体成员及文件拆分留给实施计划。它只依赖 Pangu 自有类型和必要的标准 C++ 类型，保存可独立使用的字符串、类型语义及诊断来源，不保存 Decl*、QualType、ParsedAttr、ASTContext 或常量表达式树的借用。

Attr 先完成属性解析、默认值/常量求值和声明内校验，再向 MetaIR 交付规范化语义。跨声明/TU 合并与冲突检查在完整模型上完成；同一输入与有效目标上下文得到确定结果，字段顺序与跨 TU 去重规则在实施计划中固定，不依赖哈希容器遍历顺序。CodeGen 在 ASTContext 结束后仍须能够独立消费模型。

编译选项、BuildRoot、输出路径和 Host Catalog 装配集合属于 GenerationRequest；MetaIR 明确关联一个有效目标上下文，并保存实际需要的目标相关事实，而不复制整套构建请求。不同平台、SDK 或配置的模型不得因指针宽度相同就误合并。源码位置供构建期诊断使用，默认不进入目标描述；宿主地址和布局不作为元数据身份或目标布局。

首版只有内存中的 MetaIR 与 C++ CodeGen。统一模型允许未来按实际消费者增加其他输出，但本轮不创建 Exporter 框架、不导出 JSON/二进制 Meta 文件，也不冻结 `.pgmeta` 或磁盘 Schema。CLI 的派生请求即使采用 JSON，也属于构建输入，不是 MetaIR 序列化格式。

### 4.2 目标公共支持

首版轻量公共支持放入 Foundation 的 Meta 头文件区域，由既有 Foundation 目标承载，不新增 Runtime Meta Module 或独立 Meta 库。`pg::meta` 的支持内容包括统一语义的强类型 TypeId、FieldOptions、TypeInfo / FieldInfo 只读描述及生成 Traits 的基础模板；不依赖工具、Clang、LLVM、Module 或 EngineHost。具体成员布局与公共 API 随实施计划确定，不因命名统一而冻结 ABI。

与 ModuleCodePin、宿主状态和访问接纳有关的桥接放在 Module / EngineHost 层；Foundation 及纯强类型访问代码不反向依赖这些上层能力。高层消费入口使用生成 Traits 绑定的类型与归属信息取得受保护描述，精确桥接形态留给实施计划。

构建期 `pg::meta::ir::TypeDefinition/FieldDefinition` 使用拥有数据的丰富表示，目标可消费的 `pg::meta::TypeInfo/FieldInfo` 使用轻量视图；两者是同一元数据语义的不同表示，不是两套独立反射或 Attribute Taxonomy。CodeGen 按明确映射生成选中的目标表示，不让构建期存储布局成为 Runtime ABI。

建议按消费请求生成 `TypeTraits<T>` 特化及相应入口，支持以下能力；具体函数/头文件拼写可在实施计划中统一确定：

1. 已知类型的字段访问描述及编译期遍历入口。
2. 按已知字段描述读取对象；仅在允许时提供写入。
3. 在请求类型描述的消费者中，通过高层入口取得受保护的描述借用，并在其寿命内枚举所属 Module 编译出的 TypeInfo/FieldInfo，包括不能生成访问的 Private 字段。仅请求强类型访问时，不要求同时保留这种目标描述表。

描述至少含限定类型名、可选 TypeId、字段 C++ 名称、字段键、诊断用类型名、访问级别、const 与生成只读状态。显示类型名不是持久类型编码，不输出宿主偏移量作为数据格式。

统一的是身份、类型事实和属性约束的含义及校验规则。源码来源、完整生成准备信息保留在 IR；Runtime 只携带实际消费者需要的语义。未来格式导出也须遵守该契约，不能另起一套字段身份和访问限制解释。

### 4.3 强类型读取与写入

公开可访问字段采用正常 C++ 成员访问表达式或成员指针实现，保留真实字段类型，不通过 `void*`、字节偏移或运行期类型名分派。访问入口接收对象引用，不持有对象，不创造实例身份。

读取返回与对象寿命相连的只读借用；拒绝从临时对象导出字段引用。修改通过独立写入入口完成，要求对象非 const、字段非 const、未配置 ReadOnly 且 C++ 赋值合法。写入参数的值类型与字段类型精确匹配（忽略参数 cv/ref），不接受隐式类型转换；noexcept 跟随实际表达式，不假装复杂字段赋值不会失败。

按类型遍历的可访问字段集合与完整描述集合明确区分。消费者用编译期条件判断写入能力，const / ReadOnly 字段的写入在编译时被拒绝；不把“存在字段描述”当作“可访问字段值”。Private 字段不生成访问表达式，示例通过类型已有公开方法验证其值。

示例消费者必须同时演示读、写和普通 C++ 结果断言；不能仅运行打印名称或 static_assert 元数据数量的程序。

### 4.4 描述存放与借用寿命

产物按已登记的消费需求选择。需要强类型访问时，伴随 `.gen.h` 保留调用点所需模板与类型特化；需要非内联实现或类型描述时，才生成相应 `.gen.cpp` 并编译进所属 Module，存放实现、静态字符串和 FieldInfo 表。每个描述定义只有一个编译所有者，必要导出沿用该 Module 现有导出配置。仅用于 Attr/MetaIR 检查的数据不必转换为 C++ 静态变量；仅强类型访问的类型不自动产生 Runtime 描述数组。

CodeGen 输出初始化表达式和普通 C++ 定义，由目标编译器构造目标平台上的 TypeInfo/FieldInfo。生成的 string_view/span 等视图引用目标产物自身的存储；不引用宿主工具的临时内存，不把宿主对象的字节转储作为目标描述。后续若设计数据导出，也须另行规定平台和格式表达。

生成头可以包含原始类型头；原始头默认不包含自己的生成头。公开生成头只暴露可由公开 API 合法消费的信息，不包含 Private 原始头或泄露不可命名的内部 C++ 类型。

从可卸载 Module 取得的描述通过生产可用的高层入口返回短期、仅移动的借用对象，由该对象内部持有正确所属 Module 的 ModuleCodePin。应用按已知类型调用生成的类型入口，提供 EngineHost 即可；不能要求调用方另拼 ModuleId、裸描述指针或任意回调。一个借用支持整批字段遍历，不为每个字段重复取得 Pin。开始关闭后拒绝新借用，已有借用释放后才可完成原生卸载。

这条路径必须支持没有 Service 的合法 Module，取得 Pin 与描述不能依赖测试私有访问器。现有 EngineHost 尚无此公共接缝，ModuleManager 也不保存可直接绑定任意业务描述回调的原始 Query 身份；实施必须新增、验证生成入口、所属 Module 与持有 Pin 的一致性，不能把“拿到任意 Pin”当作描述保护已经成立。不新增全局类型 Registry 或按字符串搜索任意类型的入口。

借用对象中的 string_view/span 等视图只在该借用寿命内有效，提取视图不转移其 Pin；需要跨关闭保留诊断时复制拥有型数据。用来读取对象的引用另须满足实例寿命与同步要求，CodePin 不替代 ScopeBorrow；ScopeBorrow 也不能被当作任意其他 Module 的保护。

纯粹在消费者本地实例化的模板与描述字面量按其实际存储寿命处理，不笼统要求所有编译期操作取得 Pin；但不能以“模板”名义解除对原始对象、外部函数及 DLL 存储的保护。

首版不提供可长期保存并在卸载后自行失效的通用类型句柄。需要保留诊断时只复制拥有型标量/字符串，不保留 DLL 回调、RTTI 指针、字段操作或字段表借用。

## 5. Module Query 与 Host Catalog

### 5.1 保留输入权威

ModuleDefinition、ModuleId、版本、运行期依赖和 Register 回调继续由现有 C++ 定义维护。PanguMetaTool 不解析这些值来重新构造另一个 Definition，也不新增 Module.toml、`pga::Module` 或 `pga::Service`。

ModuleId 的值只在公共 C++ 身份常量中定义一次，原 ModuleDefinition 与生成描述入口引用同一常量。CMake 登记常量的限定符号及声明头，不复制 ID 字符串；仅在私有 Definition 内定义身份的 Module 须补出公共常量并迁移原引用。生成和接纳验收须核对两条路径的身份一致，不能引入第二个身份权威来源。

每个 Module 的生成登记复用现有真实目标、Query 限定名、公开声明头及导出配置。每个 Host 显式登记自己的业务 Module 集合；CMake 将这些登记派生成请求，不依靠 Plugin 发现阶段收集全局 Catalog，也不根据偶然链接关系猜测运行期集合。

Module 的 CMake 编译链接依赖与运行期依赖仍是两张具有不同责任的图。缺失的运行期依赖按既有接纳错误处理，不由生成器悄悄加载或补齐。EngineHost 自行接纳的基础常驻根不重复加入业务 Catalog。

### 5.2 模式行为

- Modular：每个 Module 生成一个 `PanguModuleQueryV1` 原生导出包装，调用原 C++ Query；业务 Module 的原生部署、候选路径及加载仍按既有机制处理，不为 Host 生成对全部业务 DLL 的隐式导入。
- Monolithic：各 Host 生成自己的静态 Catalog，显式引用已登记的 C++ Query，并与对应 Module 的唯一库链接；生成器不生成不存在的 C++ Query 实现，不改变 Manager 的依赖顺序与注册语义。

通过正常符号引用保证静态归档内容被最终程序提取；不使用全局静态构造注册。Game / Editor 的装配集合分别验收，Module 可以完全没有 Type/Field 声明或 Service。

现有 `pangu_export_module_query()` 的对外登记方式可保留，内部改为调度新生成器。迁移后移除该目标旧 CMake 模板生成的包装，保证每个原生导出只有一个生产者；未迁移目标在过渡期维持原行为，不能同时启用两条路径。

## 6. 编译上下文、输入与产物

### 6.1 输入选择

每个 Meta 输入头只归属一个声明所有者 Module Target；在当前构建图登记时拒绝重复归属。Meta 头登记同时接入已有目标源码登记，不维护第二份独立人工头清单。公共消费者重复包含该头不重复生成实现。

扫描时遇到含 pga 声明的项目头，若既无明确生成所有者，也无相应 Meta 输入登记，必须报错要求补齐，不静默漏生成，也不在扫描后擅自增加原生输出。已登记给其他 Module 的反射头正常作为依赖处理，不重复取得生成所有权；普通无 pga 声明的依赖头不因此要求 Meta 输入登记。

首版同一个 Module Target 的 Meta 输入使用一套明确的目标编译上下文，不自动合并不同宏/选项下的不同声明，也不按各业务 `.cpp` 的临时宏环境生成多份描述。需要不同反射语义时通过切换配置重新生成。上下文来源可选现有不依赖生成输出的真实 TU，或由接线生成的最小上下文 TU；后者不引入新的手工源码 Manifest。读取实际编译数据库时，以目标及配置精确选择命令，不能只按同名源文件选第一项。

扫描按当前目标的语言、宏、目标架构、SDK/NDK、包含路径和标准库头执行；把来源 TU 替换成指定输入头的解析任务，移除 object/dependency 输出和不适用的 driver 参数。响应文件须正确展开，无法理解的上下文明确失败。工具的内建资源头配套其宿主前端，目标系统/标准库头来自目标工具链。

首版不消费 PCH 或 C++ Modules 编译产物，允许从原始头重新解析；若输入必须依赖尚不支持的编译模式，应拒绝并报告，而不是错用宿主默认语义。系统宏等差异必须由目标相关常量夹具证明。

反射类型、字段集合及其属性参数不能由 `__has_cpp_attribute(pga::...)` 或宿主/目标之间有差异的 Clang 版本条件决定；普通目标平台、架构和配置宏仍可使用。对已识别的不支持条件明确诊断，并为支持范围提供目标编译消费对照。这是项目自有反射声明的输入约束，不是禁止 SDK 系统头的一切特性探测，也不构成任意源码跨前端完全等价的保证。

### 6.2 原生构建图

建议通过一个派生请求驱动 scan、Query 包装或 Catalog 等生成任务。请求含版本、任务种类、归属目标/Host、输入根与头、输出清单、配置上下文及 Query/Host 登记；文件由 CMake 生成，不是用户另写的 Manifest。具体 CLI 和 JSON 字段拼写留给实施计划，但必须有明确格式版本、输入校验和可靠退出码。

生成输出在 Configure/Generate 时即可从已登记输入和消费需求确定。每个被选中的头/实现输出都有固定的 `.gen.h` / `.gen.cpp` 槽位，类型增删只改变内容；Query 与 Host Catalog 各有固定槽位。强类型访问、非内联实现与类型描述等需求在派生请求中明确登记，不靠生成后扫描 AST 才决定构建图里有哪些输出；也不为无消费者的信息固定生成空描述表。不在生成后 GLOB 发现新源码。

消费需求按输入头登记，头内类型采用该头的消费配置，并按所属 Module Target 汇总。同一 Module 同时被 Game/Editor 消费时，任一消费者请求描述就为该目标生成一份描述；不承诺同一个库天然为每个最终消费者保存不同内容。最终程序实际裁剪效果另行验证，精细的逐类型筛选不增加第二份手工类型清单。

建议按 Module/目标上下文批处理；任务粒度与输出粒度分开，不宣称拆成多个输出就已有 AST 增量缓存。每个输出有唯一生产者，生成任务先于所有消费者，包括公开生成头的首次编译。

工具、请求、输入和传递头依赖发生变化时，原生图正确失效。使用 Depfile 记录实际读取依赖，以成功标记配合 OUTPUT/BYPRODUCTS 的具体接线须用 CMake/Ninja 正式测试固定：内容相同不重写代码，无变化不启动工具，删除生成文件能恢复，普通无关 `.cpp` 函数体变化不触发 Meta。

### 6.3 存放、冲突与 Project 切换

继续遵守 `<EngineBuildRoot>` / `<ProjectBuildRoot>` 分根、`Generated/PanguMeta/<Config>/<CMakeTarget>/`、Public/Private 和 `.gen.h/.gen.cpp`。输入映射保留所属输入根及相对路径，拒绝逃逸或同名覆盖；机器绝对路径不进入生成符号或公开包含名。

**同一 Engine 工作区只服务一个当前 Game Project。** Engine 生成代码直接放在上述所属目标目录的 Public/Private 下。切换 Project 时复用同一 EngineBuildRoot，新 Project 的配置成为当前配置，并按需覆盖之前的 Engine 生成代码及受影响的编译产物。

首版同时落实 Engine 自有目标的对象文件、最终库、导出头和 Meta 产物归属 EngineBuildRoot，Project 自有目标归属 ProjectBuildRoot。这是新增构建整理范围：现有嵌入式夹具把 Engine binary 子树放在 ProjectBuild/Engine，库及导出头也取顶层 Project 构建根，不能仅调整 Meta 路径就宣称完成。保持一个 Module 一个真实库及 Project 原生目标依赖，不以源码复制、重复目标或第二套调度器实现分根。

Project 切换必须重新 Configure 当前 Project，更新 Engine 侧共用位置的当前派生请求、输出清单及真实编译配置。当前 Project 的来源也进入生成任务输入；即使两个 Project 的宏暂时相同，接线仍须识别当前配置已经切换。切到 B 后直接构建旧 Project A，须由原生依赖识别切换并触发 A 重新 Configure，再继续构建；无法恢复则明确失败，不能直接把旧图或成功标记视为仍然有效。自动重配满足这里的切换要求，不另加每次无变化构建都运行 PanguMetaTool 的检查。

同一 EngineBuildRoot 的 Configure/build/test 会话串行，切换前结束上一 Project 的构建会话；保留平台 BuildRoot、Config 与实际目标名的既有布局。输入、宏、SDK/ABI、模式及所属 Project 变化使相关生成任务失效，内容相同仍按差异写入规则复用代码；正常 C++ 依赖决定重编译范围。切换不要求无条件删除整个构建树，也不将过期成功标记当作复用依据。

### 6.4 失败与原子发布

工具先完成全部输入和模型校验，再生成候选内容。仅在全部候选准备成功后发布；单文件以同文件系统临时文件替换，内容相同保留原文件时间戳。多文件不冒充操作系统级原子事务，成功标记最后提交，消费者通过任务依赖观察整批完成。

失败、取消或任一发布失败均不更新成功标记，返回非零并阻断消费者；已有文件不能使本轮任务被判断成功。下轮依据全部输入重试并修复可能的部分发布，不能仅凭旧代码存在跳过。输出集合改变时，由当前请求清理本任务拥有的废弃产物，不扫描或删除其他目标目录。

Driver、AST、属性、模型和发布任一 Error/Fatal 均使任务失败；不能只相信 ClangTool 返回值。Meta 检查移除未知属性豁免并恢复严格诊断；目标侧仅为实际消费属性头的目标和必要消费者传播受控豁免，其余警告仍按既有策略执行。

## 7. 宿主构建与 SDK

PanguMetaTool 是独立宿主 C++23/Clang 工具，不继承 Android/iOS 目标 Toolchain；工具及 SDK 位于宿主，生成代码由目标工具链编译。复用现有独立 BuildTools 的宿主准备与测试调度思路。启用任一 PanguMetaTool 任务就要求准备完整工具及匹配 SDK，包括只有 Query/Catalog、没有 Type/Field 输入的目标；只有完全不启用此类任务的构建免除此要求。

LLVM/Clang 开发库须显式准备，版本、标准库与 ABI 匹配宿主工具。Windows 使用 MSVC STL，Linux/macOS 使用 libc++；自有 Attr、Main、CodeGen 及所需 SDK 继承关系均须满足 RTTI 链接要求，不保留 Windows `-fno-rtti` 例外。必要时重建匹配且启用 RTTI 的开发库，不替换目标 clang，不让日常引擎构建隐式构建 LLVM。

首版提供正式、可复用的显式 SDK 准备流程及版本/ABI/RTTI 检查，必要时给出依赖库构建步骤；新检出不依赖 `.probe/` 或旧机器缓存。首版不交付预编译 SDK 安装包，分发及升级另行设计。生产支持三桌面宿主；Android/iOS 由桌面工具交叉解析，不在移动设备运行生成器。

工具可由独立原生 Ninja 工程增量构建；其二进制和源/配置依赖必须进入消费者原生图。普通无变化构建不为“检查工具是否变化”无条件运行嵌套构建或扫描。独立工具缓存的重建同样遵守同 BuildRoot 会话串行规则。

## 8. 正式验收设计

所有有效测试迁入正式 `Tests/`，按现有 BuildTools 与集成测试接线分层；历史探针只作输入，不成为正式验收依赖。不因文档中的预期矩阵声称实现或测试已通过。

| 验收方向 | 必须观察到的结果 |
| --- | --- |
| 无参数 Type | 无 TypeId 也能生成并消费描述与强类型访问；重命名不伪造稳定身份 |
| 显式 TypeId | 格式/零值/重复拒绝；同一声明重复包含去重；不同 ID 不串用 |
| 字段键 | 默认名称、显式稳定键、重命名保留显式键；含 Private 的键冲突和非法常量拒绝 |
| 属性与 Options | 正确大小写、数量、类型、默认值、常量对象/工厂；拼写、裸命名参数、未知属性、运行期输入可靠失败 |
| MetaIR 与统一语义 | Attr/ASTContext 销毁后模型仍可被 CodeGen 消费；缺省值、Key、const/ReadOnly 等从 IR 到 TypeInfo/FieldInfo 含义一致；跨 TU 去重、冲突及确定性有正式断言 |
| 按需输出 | 按头登记、按 Module 汇总需求；同头类型共享消费配置；Game/Editor 请求并集仅生成一份；无描述消费者时不生成 Runtime 描述表，IR 检查继续有效；首版无 Meta 文件输出依赖 |
| 真实对象操作 | 至少包含 bool、整数、浮点、枚举和一个普通对象字段；消费者实际读写，普通 C++ 核对结果 |
| 访问约束 | const 对象、const 字段、ReadOnly、错误值类型和临时对象借用的编译拒绝；Private 仅描述，已有公开接口仍可使用 |
| Module 无反射 | 仅生成 Query/Catalog 也可正常装配；不要求 Service 或 Type |
| Query 与 Catalog | 两模式真实加载/最终链接；每个原生导出一个定义；Game/Editor 集合隔离，静态归档正确提取 |
| 注册与关闭 | 原 Register 回调和失败回滚继续有效；生成器不另建注册生命周期或全局静态构造 |
| 可卸载描述 | 无 Service Module 经生产高层入口取得仅移动、自持正确 Pin 的描述借用；关闭拒绝新借用，旧借用阻止完成卸载；释放后观测真实物理卸载，拥有型复制诊断仍可检查；错误身份绑定须拒绝 |
| 实例寿命 | 经 EngineHost 具名入口取得 ScopeBorrow 后实际访问服务中的反射对象；Borrow 阻止提前销毁，释放后可完成关闭 |
| 编译上下文 | 每 Module 一套明确上下文；桌面及移动目标宏/指针宽度/SDK 常量由目标编译器核对；已识别的不支持前端条件可靠拒绝，不混用 IR 或宿主对象内存 |
| 增量与恢复 | 无变化不运行工具；无关函数体不生成；传递头/参数/工具变化失效；同内容不重写；丢失产物恢复；输入删除清理自身废弃文件 |
| 失败发布 | 首次失败、已有输出后的失败、受控中断及发布失败阻断消费；下轮恢复，不拿旧成功标记冒充本轮成功 |
| Project 切换 | Engine 对象/库/导出头/Meta 与 Project 产物实际分根；A→B→直接构建 A 能原生重配恢复或明确失败；宏/SDK/模式变化及相同参数切换正确失效，无过期成功标记误用 |
| 登记与身份 | 每头唯一所有者，登记接入目标源码；孤立 Field、未知所有者/漏登记头报错，其他已登记 Module 作为依赖；C++ 公共 ModuleId 常量由 Definition/生成入口共同引用，CMake 不重复值 |
| 路径与映射 | 同 basename 头、不同输入根、空格/中文路径及目录逃逸边界；不生成机器路径符号 |

三桌面分别验证宿主工具与实际消费运行，并分别验证 Monolithic / Modular；已有有效 Module、EngineHost 和独立 Project 覆盖保留。**本轮 Android 只开展 ARM64（arm64-v8a）工作与验收**：检查工具目标语义、生成消费编译链接及正式 Host 两模式最终链接，使用既定 arm64 preset；不增加其他 Android ABI 的实现或测试任务。iOS Device ARM64 完成两模式最终链接及产物检查，不运行交叉目标 GTest，不宣称设备、签名或安装通过。历史 PoC 的其他 ABI 记录保留为历史证据，不转换为本轮工作要求。

动态卸载夹具不得因消费者直接导入业务描述入口而保留额外原生引用；通过受保护的动态测试入口读取真正 DLL 存储，以库级事件确认物理卸载。已知类型的普通导入消费另行验收，不以其逻辑关闭冒充物理卸载。

新增/修改 C++ 与生成结果使用仓库 clang-format、clang-tidy 及真实目标编译数据库检查。设计中尚未实现的属性与接口示意不冒充已编译 API。SDK 准备、工具首次构建、Meta 生成及目标编译分别计时，记录增量/no-op、生成体积、最终二进制/描述成本及直接 C++ 与强类型访问对照。本轮建立可复现基线，不设未经测量的数值阈值；但无变化不启动 PanguMetaTool、不重编、不重链接，无关函数体不生成及同内容不重写均为硬性要求。

## 9. 实施接缝与文档同步

实施计划可依次拆成：Engine/Project 实际产物分根与切换先导验证 → 宿主 SDK/RTTI 准备 → 独立工具与 Foundation 轻量支持 → Attr/MetaIR/输入登记 → 强类型生成及受保护描述消费 → Query/Catalog 与共享身份登记迁移 → 原生依赖/发布 → 正式测试、平台矩阵与规范同步。这里是规划接缝，精确任务及接线由后续实施计划记录。

实施时同步 Reflection / Meta、构建系统、工具链和 Tests/BuildTools 文档，清楚区分 Draft、已确认设计和实际实现状态。原 PoC 数字字段 ID、bool/int Options 及历史生成布局保留为历史记录，不继续作为正式参数协议。

本规格不会自行提升公共 C++ API/ABI 为 Frozen；精确文件拆分、类/函数名、诊断码和 CLI/JSON 拼写在实施计划中统一记录。SDK 发行、动态反射 Registry、持久化迁移、完整 Inspector 以及 Private 自动访问保留为后续专题。

MetaIR 复用统一元数据契约，具体目录和 C++ 成员仍属实施设计；JSON/二进制 Meta 导出、磁盘版本与兼容性协议在有独立消费者时另行设计，不以当前内存模型提前冻结。
