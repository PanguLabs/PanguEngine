# PanguEngine 内存管理规范

> 设计状态：Frozen（Memory Ownership Contract v1）；具体 API 与实现不由本规范宣称完成
> 更新：2026-10-20

本文规定内存管理实现必须满足的约束；类型和接口名称表示设计约定，不代表已经落地。条款使用“**必须**”（MUST）、“**应该**”（SHOULD）和“**可以**”（MAY）区分约束强度。

本文的 `Module` 遵循 [Plugin / Module](plugin-module.md) 的定义：一个逻辑代码单元对应一个 STATIC/SHARED 库 Target，不指 C++ 语言的 Module，也不与 Plugin 混称。Plugin 是分发与发现单元，可以包含多个 Module 或仅包含 Assets。STATIC Module 不具有独立的运行时可卸载镜像；静态链接构建同样遵守所有权契约，代码驻留保护覆盖实际承载代码的 EXE 或动态库。

## 10 条核心规则

1. **所有权优先，分配器其次。**（Ownership first, allocator second.）
2. **引擎原生 Allocator 使用静态接口。** STL 边界的 `std::pmr` 适配和跨 Module 的 C ABI 回调是明确允许的边界机制。
3. 默认分配器为 `SystemAllocator`；专用分配器依据生命周期、访问模式和测量结果选择。
4. 生命周期受控、能够统一回收的帧内临时内存应该使用 `LinearAllocator`；回收条件见下文。
5. 高频创建、销毁的固定大小对象可以使用 `Pool` / `Slab`，但必须评估线程模型、内存占用和实际性能。
6. `EngineHost`、`EngineContext`、`WorldContext` 等明确的生命周期作用域，或由其持有的 `Service`，可以拥有独立的 `Arena`；必须明确 Owner、Allocator Provenance、Borrow 失效条件及安全重置与销毁顺序。不为此引入 `Subsystem` 架构。
7. 跨 `Module` 的所有权（Ownership）必须由明确的 ABI 契约（ABI Contract）约束。
8. 资源生命周期（Resource lifetime）与内存生命周期（Memory lifetime）是两个不同的概念。
9. GPU 资源采用 **Handle + 延迟销毁（Deferred Destruction）**，而不是通过裸指针直接管理所有权。
10. Debug / Development 构建可以启用完整的内存诊断（Memory diagnostics）；Shipping 构建的可选诊断开销应该接近零，并保留正确性所需的状态和同步。

## Pangu 内存所有权契约 v1（PANGU MEMORY OWNERSHIP CONTRACT v1）

1. 每一次内存分配都必须具有明确的分配器来源（Allocator provenance）。
2. 释放内存时，**必须**遵守创建该分配的分配器契约（Allocator contract）。
3. 如果内存由另一个 `Module` 分配，当前 `Module` **不得**擅自使用自身的 CRT 分配器释放这块内存；释放必须回到原分配域，或使用分配器契约明确允许互相释放的等价分配域。仅凭 Module 的 ABI 兼容或分配器类型相同不能认定分配域等价。
4. 拥有所有权的 Pangu 值类型（Owning value types）**必须**封装其销毁方式与内存分配策略。
5. 借用视图（Borrowed views）**不得**暗示或转移所有权；失效条件和使用范围必须遵守下文的借用契约。
6. 资源句柄（Resource Handles）引用由 `ResourceRegistry` 持有的资源；调用方通过 Registry 申请释放，**不得**直接释放底层资源。
7. 返回具有所有权的裸指针的 C ABI 函数，**必须**同时提供由创建方 `Module` 实现的配套销毁函数。
8. `std::pmr::memory_resource` 的生命周期**不得**超过其底层分配器（Backing allocator）。
9. `std::pmr` 容器的生命周期**不得**超过其使用的 `memory_resource`。
10. `Module` 必须满足下文的卸载前置条件后才能卸载；卸载后不得调用其代码或访问依赖其状态的对象。
11. Shipping 构建的正确性**不得**依赖内存分配追踪、调用栈记录、金丝雀值（Canaries）或调试元数据。
12. Debug / Development 构建**可以**附加 `Domain`、`Tag`、分配统计、保护机制和诊断信息。
13. 原生分配器通过具体类型、模板或 Concept 表达静态接口；运行时适配范围遵守核心规则第 2 条，不将边界机制扩展为所有分配器的统一虚基类。
14. 分配策略（Allocation strategy）和所有权语义（Ownership semantics）是相互独立的概念，**不得**将两者混为一谈。

## 分配器操作契约

分配器来源包含实例或可互相释放内存的等价分配域，不能仅凭类型相同判断。来源可以由类型、所有者或上下文表达，不要求每次分配都附带运行时标签。

每个分配器的接口文档必须明确以下行为；未声明的能力不得假定存在。

| 项目 | 必须明确的约束 |
| --- | --- |
| 大小与对齐 | 声明最大请求大小、支持的对齐及默认对齐；对齐必须为非零的 2 的幂。计算元素总大小、填充和头部大小时必须检查溢出，失败时不得返回不足大小或错误对齐的内存。 |
| 零长度请求 | 声明是否接受零长度及其返回值、释放方式；不得将零长度的正常结果与分配失败混淆。适配 STL 时必须满足标准接口契约。 |
| 释放 | 声明是否需要原始大小和对齐、是否接受空指针，以及允许执行释放的实例或分配域；有效释放必须不抛异常。重复释放和来源不匹配属于契约违例。 |
| 单独释放与批量回收 | 声明是否支持单独释放；线性分配器的释放适配可以是无操作，但必须说明实际回收时机。 |
| 重新分配 | 声明是否支持、指针及借用的失效条件、零长度语义；可恢复的重新分配失败必须保留原分配及内容。原始字节搬移不得代替非平凡对象的移动与析构。 |
| 线程模型 | 声明实例是线程独占、需要外部同步还是内部线程安全，并分别说明并发分配、跨线程释放和重置限制。分配器线程安全不代表其中对象可并发访问。 |

## 禁用异常与分配失败

- 引擎原生分配接口必须区分可恢复失败与失败即终止的路径。`try_allocate` 一类接口通过显式结果报告内存不足、大小溢出或不支持的请求，调用方必须处理失败；具体结果类型由接口设计确定。
- 失败即终止的分配接口必须在名称或文档中声明策略。失败时进入所有构建配置都有效的致命错误处理路径，不能仅依赖 Debug 断言，也不能返回无效指针让调用方继续执行。
- 需要恢复的调用链必须从分配到对象创建、容器扩容都显式传播错误，并清理已取得的资源；仅把底层分配替换成 `try_allocate` 不足以使上层操作可恢复。
- 本项目的 PMR 适配层采用分配失败即终止策略。标准 `memory_resource::do_allocate` 要求成功时返回满足大小与对齐的存储，失败时抛出异常；在项目禁用异常的运行约定下，适配层必须在失败时终止，不能返回 `nullptr` 作为替代失败协议。需要恢复的场景使用原生显式错误接口及相应容器。
- 所选标准库在禁用异常配置下的失败行为必须通过构建配置与针对性验证确认；PMR 容器自身的长度错误等失败路径也必须纳入验证，不能假定全部失败都经过适配层。

PMR 的标准分配、释放与资源等价要求见 [C++ 标准草案：memory_resource](https://eel.is/c++draft/mem.res.private)。项目的失败即终止策略是禁用异常环境的约定，不是标准提供的可恢复模式。

## 临时内存、对象与借用生命周期

- `LinearAllocator` / `Arena` 的重置、回退、销毁或底层存储复用，必须等待所有访问受影响内存的任务结束，并阻止新的访问。CPU 帧结束本身不是安全回收判据；GPU 可访问的存储还必须满足 GPU 完成条件。
- 原始存储回收不自动承担对象析构。重置前必须完成需要执行的析构和资源清理；若 Arena 提供析构登记机制，必须明确责任及顺序，避免遗漏或重复析构。
- 分配器或 `memory_resource` 对象仍然存活，不代表其分配的存储仍有效。容器必须先销毁或以明确支持的方式解除对旧存储的依赖，之后才能回收；例如 `vector::clear()` 通常保留容量，不能据此重置其底层 Arena。
- 普通借用视图（指针、引用、`span`、`string_view` 等）本身不延长所有者、分配域或资源的生命周期。接口必须说明所有者销毁、容器扩容、元素删除、内存重置等操作对指针、引用和视图的失效影响；失效后不得通过借用访问对象。
- [Service](service.md) 的 `ServiceRef` / Borrow / Lease 是显式生命周期保护机制，Owner 必须等待其释放才能销毁受保护实例；它们不等同于普通借用视图，也不转移实例所有权。CodePin 只保护代码驻留，不能单独保证实例或其存储有效。
- 异步任务保存借用时，必须由任务依赖、拥有型对象或其他明确机制保证整个访问期间的有效性，并满足对象自身的同步要求。局部作用域或当前帧的借用不得无约束地逃逸到异步任务中。

## 资源句柄与 GPU 回收

- 句柄类型必须区分拥有型与非拥有型语义。拥有型句柄维持 Registry 中的存活依赖，销毁或显式释放句柄时解除该依赖；非拥有型句柄仅标识资源，不阻止回收。具体采用引用计数、显式依赖记录或其他机制，由资源系统决定。
- Registry 负责处理释放请求并决定资源何时可回收。请求释放不等于立即销毁；依赖尚未结束时必须保留必要的底层资源，并明确此时是否还允许取得新的访问。
- 句柄查询必须识别空句柄、已失效句柄和错误的资源类型，并给出明确的失败结果。槽位复用必须防止旧句柄误指向新资源，可以使用 generation 或等价机制；这些正确性要求同样适用于 Shipping。
- 从句柄解析得到的指针仍是借用。查询成功不自动保证后续访问安全；并发释放时必须通过拥有关系、访问保护或同步机制覆盖整个访问期间。
- GPU 资源的逻辑失效与底层销毁必须分开。开始回收前必须阻止新的使用，并处理已经记录但尚未提交的命令；底层资源及关联分配只有在所有相关队列完成最后一次使用后才可销毁或复用。
- GPU 完成状态通过 Fence、Timeline 或具有明确同步保证的等价机制判定。仅等待固定帧数不构成安全证明；多队列使用必须覆盖全部相关依赖。提交和完成信息在底层资源释放前必须保持有效。

## Module 边界与卸载

- 跨 Module 的 C ABI 可以通过函数指针和不透明上下文提供分配、释放或销毁能力。契约必须明确调用约定、参数布局、所有权、线程要求以及代码和上下文的有效期；函数指针不会自动延长 Module 的生命周期。
- 配套销毁函数负责对象析构和匹配的存储释放。调用方必须保留所需的销毁入口与上下文；即使存储来自宿主，只要析构函数、deleter 或回调依赖某个 Module，该 Module 仍必须保持加载。
- STL 容器和 `std::pmr::memory_resource` 不作为稳定 C ABI 的交换类型。同一受控构建内若通过 C++ 接口跨 Module 传递这些类型，必须另行约定编译器、标准库、构建选项和生命周期兼容性。

Module 卸载必须按以下依赖顺序完成：

1. 停止接受新的业务调用、任务和资源使用请求，并阻止新的业务回调进入；保留卸载清理所需的销毁与释放入口。
2. 等待正在执行或已经排队的相关调用和任务结束；等待 GPU 使用满足完成条件。
3. 在 Module 代码和分配器仍有效时，移除回调注册，处理相关延迟销毁队列，销毁依赖该 Module 的对象，并解除外部持有的相关所有权和借用。
4. 确认没有存活分配或其他操作继续依赖待销毁分配器后，销毁其上下文与分配器；所有清理代码执行完成并释放最后一个必要 CodePin 后，才允许卸载实际承载代码的动态库。STATIC Module 的归档本身没有独立卸载操作。

任一前置条件无法满足时，必须拒绝或推迟卸载，不能通过清空登记信息掩盖仍然存在的依赖。

## STL / PMR 适配边界

PMR 用于需要运行时选择分配域的 STL 边界，不要求所有引擎容器使用 PMR。适配层必须保持后端的对齐、释放来源和线程约束；`do_is_equal` 只有在两个 resource 的分配确实可以互相释放时才能返回 `true`。

| 容器操作 | PMR 分配域规则 |
| --- | --- |
| 普通复制构造 | 使用复制时的默认 resource，不自动保留源 resource。需要保留或选择分配域时，必须使用显式指定 allocator 的构造方式。 |
| 普通移动构造 | 继承源 allocator；移动到较长生命周期的对象中不会延长源 resource 或底层存储的生命周期。 |
| 显式指定 allocator 的复制或移动构造 | 使用指定分配域；移动时若 resource 不等价，可能发生重新分配和逐元素移动。 |
| 复制赋值或移动赋值 | 不传播 PMR allocator，保留目标分配域；resource 不等价时不能假定移动赋值只转移存储。 |
| `swap` | 不交换 PMR allocator；仅允许在 resource 等价时执行，resource 不等价时行为未定义。 |

跨生命周期或分配域传递数据时，必须检查操作后的实际分配器及嵌套对象所依赖的存储；外层容器使用某个 resource 不意味着任意元素类型的内部存储也使用该 resource。默认 resource 应在受控初始化阶段确定，不作为临时切换分配域的手段。

上述传播规则依据 [polymorphic_allocator](https://eel.is/c++draft/mem.poly.allocator.class) 与 [Allocator-aware containers](https://eel.is/c++draft/container.alloc.reqmts)，实现时以项目采用的 C++23 标准库为验证对象。

## 诊断与验证

- Shipping 可以去除调用栈、额外追踪表和其他可选诊断，但必须保留分配器必要状态、正确释放所需的信息、句柄有效性机制、同步与 GPU 完成记录。
- 声称诊断接近零开销时，应明确关闭了哪些功能，并通过生成代码或测量验证；不将分配算法本身的时间、空间成本算作可消除的诊断开销。
- 实现落地后，针对性验证至少覆盖：对齐与大小溢出、分配失败及终止路径、声明支持的跨线程释放、存储重置前的析构与任务完成、过期句柄及槽位复用、多队列延迟销毁、带未完成依赖的 Module 卸载，以及 PMR 跨分配域的复制和移动。
