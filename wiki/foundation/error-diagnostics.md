## 当前正式实现切片（2026-10-22）

已新增 `Source/Runtime/Foundation/` 的真实 `PanguFoundation` STATIC Module（一个 CMake Library Target）：

- `Public/Error.h`：`pg::ErrorDomainId`、`pg::Error`、`pg::NativeErrorCode` / `NativeErrorSourceId`；无字符串指针、虚表、共享插件状态和默认 Error 成功哨兵。编译期错误域用 `ErrorDomainId::Constant<非零数值>()`，来自外部的数字用 `TryFromRaw()` 显式拒绝全零；Native Code 使用 `std::optional` 明确是否存在，零值本身不是缺失。
- `Public/Result.h`：`pg::Result<T> = std::expected<T, pg::Error>`、`pg::Status = Result<void>`。返回它们的可失败业务函数仍须自行标注 `[[nodiscard]]`，错误传播使用 `std::unexpected`。
- `Private/Error.cpp`：非 `constexpr` 的 `pg::MakeError` 便利入口；其有无及签名不是冻结 ABI 要求。
- `Tests/Foundation/ErrorTests.cpp`：覆盖常量构造、强类型身份、零域拒绝、显式 Native Code、`Status` 成败、`Result` 原错误传播，以及类型的拷贝/布局基本性质。Windows、WSL Ubuntu、macOS 的 CTest 运行已通过，Android/iOS 的 `PanguFoundation` 静态库目标编译已通过。

**明确仍未冻结**：`ErrorDomainId` 临时采用 64 位数字的选择及其分配治理；`NativeErrorSourceId` 编码；`pg::Error` 的精确内存布局、对齐与五平台跨动态库 ABI；错误字典/外部报告的实现。当前实现使用 `std::optional<NativeErrorCode>` 按值存储，不应在 ABI 合同和验证通过前作为可卸载 Plugin 的已认证 Public ABI。此切片不包含 ErrorReport、Logging、Check/Fatal、全平台系统错误捕获，也不改变本文件既有 Frozen **语义**。

## 1. 目标与适用范围

本规范设计引擎、工具和 Plugin 共用的失败表达、传播与基础诊断契约。目标是让调用方明确区分“操作失败但状态有效”和“进程已经不能安全继续”，并保证诊断设施不会破坏 Module 卸载、Scope 所有权或无异常约定。

既有 Frozen 前提保持不变：使用 C++23、禁用 C++ Exception；可恢复错误显式返回；析构与释放不依赖异常；PMR 分配失败进入终止路径；Shipping 正确性不依赖可选诊断。

本文件冻结错误表达、失败报告、断言、日志与应急路径的语义契约。MUST / SHOULD / MAY 分别表示必须、应该和可以；具体冻结与未冻结范围见第 13 节。设计确认不代表实现完成或平台验证通过。

v1 覆盖错误值、Result、错误传播、Assert/Check/Fatal、普通日志、最小应急输出及它们的生命周期。不规定完整 Profiler、遥测平台、Crash 上传、符号服务器、Editor 日志界面或第三方日志库选型。

## 2. 方案选择

| 方案 | 收益 | 代价与限制 | 决策 |
| --- | --- | --- | --- |
| 结构化值错误 + `std::expected` + 独立诊断 | 传播成本可控；可按错误身份分支；错误本身不依赖插件代码驻留 | 详细上下文需要显式收集；不能自动获得完整原因链 | 采用 |
| 统一使用整数或单一全局错误枚举 | 简单、无需动态分配 | 错误域容易混淆；所有业务争用全局枚举；扩展性有限 | 仅用于有独立约束的底层适配 |
| 默认携带字符串、堆对象与原因链的错误对象 | 信息丰富，适合离线诊断和复杂工具报告 | OOM、跨 Module 析构、传播成本和生命周期更复杂 | 可作为上层显式报告，不作默认错误值 |

不直接把 `std::error_code` 选为跨可卸载 Module 的统一错误表示：标准对象关联一个 `error_category` 对象，消息解析也通过该对象。类别对象及其实现的驻留需要额外约束。这不是禁止局部使用标准错误码；平台和第三方适配层应在边界转换为引擎值错误。标准依据见 [C++23 草案 N4950：error_code](https://timsong-cpp.github.io/cppwp/n4950/syserr.errcode)；卸载风险是结合本项目 Module 契约得出的设计判断。

## 3. 失败分类与处理选择

| 情况 | 表达与处理 | 示例 |
| --- | --- | --- |
| 正常业务结果 | 普通值、枚举或 `optional`，由接口说明 | 查询未命中且“缺失”属于正常结果 |
| 可恢复操作失败 | `Result<T>` / `Status`，调用方处理或传播 | 文件打开失败、配置错误、无可用设备 |
| 有效输入之外的外部数据 | 显式校验并返回错误 | 损坏的资源文件、用户输入、网络数据 |
| 取消、超时、暂不可执行 | 显式结果，说明副作用和完成状态 | Cancelled、Timeout、Busy |
| 内部契约违例 | Debug Assert 或始终有效的 Check，按下文区分 | 不变量失效、内部索引错误 |
| 不可恢复失败 | Fatal；最小诊断后终止进程 | 无法维持内存安全、失败即终止的分配路径 OOM |

“可恢复”表示当前操作可以把控制权交回调用方，且其承诺的状态仍有效；不承诺调用方一定能重试成功。启动配置错误可以通过正常回滚结束应用，不必进入 Fatal。设备丢失是否可恢复由 Renderer 契约决定。

错误不自带日志严重级别。同一个“文件不存在”，在探测可选配置时可能无需日志，在加载必需资源时才需要报告。`LogError` 只记录事实，不改变控制流。

## 4. Error：默认无堆分配的结构化值

### 4.1 数据与成本

默认 `Error` SHOULD 是小型、固定大小、可按值复制的对象；构造、复制、移动、比较和销毁 MUST 不分配堆内存、不抛异常，也不查询 Registry、日志系统或线程局部“最后错误”。

| 逻辑数据 | 语义 |
| --- | --- |
| Error Domain ID | 错误域的稳定值身份，独立于 Provider ModuleId |
| Code | 域内显式分配的代码，表示可以由程序判断的失败原因 |
| 可选 Native Code | 保留原始平台/第三方错误的来源标识及数值；必须显式表达“未提供”，不能仅用数值 0 推断 |

这是语义表，不是已冻结的内存布局。Error MUST 不包含字符串指针、`string_view`、虚表、回调、`std::error_category*`、堆拥有对象、ModuleCodePin 或失败报告指针/关联句柄。错误值单独存活不能阻止 Module 卸载，也不依赖查找报告才能判断控制流。

Error 只表示失败，不再增加一个与 Result 成功状态重复的 `Success` 错误码。错误构造接口必须避免产生无有效错误域的“默认成功 Error”。

完整文本、路径、源位置、调用栈及原因链不进入默认 Error；重要操作通过第 5.4 节的独立有界失败报告保留现场。其他需要丰富信息的接口可以显式提供有清晰所有权的领域报告，并说明成本。

### 4.2 身份与匹配

- 每个领域使用自己的强类型代码定义，并显式指定对外代码值；不得依赖枚举声明顺序形成持久协议。
- Error Domain ID 不得来自地址、RTTI、`std::hash`、装载顺序或运行时自增注册序号。具体位宽和分配工具与后续身份规范协调；发布前必须验证身份唯一性。
- 一个 Module 可以提供多个错误域；多个实现同一契约的 Provider 可以使用同一契约错误域。ModuleId 不代替 Error Domain ID。
- 处理分支按 Domain ID + Code 判断，不能解析消息文本。Native Code 用于进一步诊断或接口明确允许的细化判断。
- 未识别的域或代码仍是有效失败，必须能够原样传播和数值输出；不能因缺少消息字典而调用失效代码或自行判为成功。
- 已发布的错误身份不得换作另一种含义。显示文本可以修改，不改变身份；运行时值布局不自动成为磁盘或网络格式。

内置错误文本可以由常驻代码提供。Plugin 错误字典如需注册，应使用既有 Module 注册流程，将纯数据复制到诊断设施持有的存储；不得登记卸载后仍会调用的消息转换函数。字典不可用时退化为数值输出。注册资源不足须明确失败或退化，不影响 Error 的创建与传播。

### 4.3 系统错误捕获

平台适配层 MUST 在原始失败后、调用日志或其他可能改变错误状态的 API 前，捕获对应的原始错误码。不得无条件读取一个 API 未声明有效的 `errno` / last-error。

转换应保留原始来源和数值；多个平台错误映射为同一引擎代码时，不能因此丢失诊断依据。第三方抛异常接口不因返回外层 Result 就变成无异常接口，应选用其显式错误路径或另行设计符合工具链政策的隔离边界。

## 5. Result 与传播规则

### 5.1 返回形式

公共可恢复失败接口统一采用 `std::expected<T, Error>`，无成功载荷时采用其 void 形式。v1 使用标准类型别名，不另造 expected 实现；`pg::Result<T>` / `pg::Status` 为命名方向，最终头文件和公开名称仍待 API 设计确认：

```cpp
// 接口方向示意；Error 须由正式头文件完整定义。
namespace pg
{
template <typename T>
using Result = std::expected<T, Error>;

using Status = Result<void>;
} // namespace pg
```

- 返回 Result/Status 的可失败函数 MUST 标记 `[[nodiscard]]`；不得假定类型别名本身就提供这一诊断。
- 错误路径使用 `std::unexpected(error)`；成功的 Status 使用成功状态，不返回伪造的零错误。
- 模块内部的紧凑算法可以使用领域专属 `std::expected<T, E>`，但必须在公共边界明确转换。无需让每个布尔查询都变成 Result。
- `noexcept` 表达“不向外抛出异常”，不表达“不分配”“不会失败”或“所有 OOM 都可恢复”。是否标注必须与整个调用链契约一致。
- Result 中成功值 `T` 的构造、移动、析构和分配成本仍由 `T` 决定；无堆分配的 Error 不意味着任意 `Result<T>` 都无分配。
- Result 只承诺接口声明的失败可以返回，不默认承诺 OOM 可恢复。只有明确声明支持可恢复 OOM 的接口，才必须让包括成功值构造、错误传播和回滚在内的整个路径满足该要求；其他接口沿用其声明的分配策略。

### 5.2 访问与传播

先检查 `has_value()` 或布尔状态，成功时使用解引用/箭头访问值，失败时访问 `error()`。不使用 `value()` 作为失败检查或引擎 Fatal 入口，因为其失败语义是抛出 `bad_expected_access`；`operator*` 也不能替代状态检查。依据 [C++23 N4950：expected observers](https://timsong-cpp.github.io/cppwp/n4950/expected.object.obs)。

```cpp
// OpenInput / BuildFromInput 为业务占位名称，只示意传播方式。
auto input = OpenInput(path);
if (!input)
{
    return std::unexpected(input.error());
}
return BuildFromInput(*input);
```

1. 调用方必须选择处理、传播或显式接受失败。刻意忽略必须在代码中说明理由及不受影响的不变量，不能普遍用 `(void)` 消除提示。
2. 传播层默认原样返回错误；确需改变抽象层次时，应给出明确映射，并保留必要的 Native Code 或显式领域报告。
3. 重试必须由知道幂等性、预算和取消状态的调用方决定；错误类型不自动触发重试。
4. 对象创建失败时先清理已取得资源，再返回失败；避免把半初始化对象暴露为成功值。需要失败报告的创建流程采用显式工厂/初始化协议。
5. 默认只在负责处置结果的边界报告一次最终失败，例如命令入口、资源加载请求或 Host 启动入口；各传播层不能重复打印同一错误。

需要沿调用链收集的详细上下文通过第 5.4 节的显式诊断上下文传递；不得以 TLS 最后错误或全局可变 Error 替代返回值。

普通日志记录的是“报告位置”。如果没有采集失败起源，不能把最上层日志的 `source_location` 宣称为原始失败位置；起源位置应显式保存为可安全持有的数据。

### 5.3 失败后的状态

每个有副作用的可失败接口 MUST 声明：失败后未改变状态、已经回滚，或部分完成并通过显式数据说明进度。单一 Error 不足以表达的“已写入字节数”等信息，应该使用专门的结果结构。

取消请求不等于任务已经结束；Timeout 不等于操作未执行；Busy 不等于停止成功。调用方必须继续遵守任务、Borrow、资源和 CodePin 的存活要求。

析构函数不能返回 Result。需要向调用方报告的提交、Flush、Close 等操作，应有显式可失败入口；析构只执行约定的兜底释放，不能把不可见的析构日志当成成功提交的证据。

### 5.4 操作级失败报告

资源加载、Host 启动、工具命令等重要操作 MUST 提供独立于普通日志的有界失败报告，以免日志丢弃后失去失败现场。报告由操作入口拥有，通过显式诊断上下文向下传递；操作完成后交付调用方，使其同时掌握 Result 和报告。普通底层函数不必独立创建报告。

- 报告保留主错误身份、所选主错误的原始失败点和必要上下文；容量不足时标记截断，优先保留主错误及其现场，不让后续补充信息挤掉主错误。可选报告未提供或内容被截断时，Error 仍可独立处理；重要操作不能以普通日志替代报告。
- 报告在操作开始前确定存储预算，收集过程不能隐式扩容。明确支持可恢复 OOM 的路径还必须覆盖报告存储准备、记录和交付的失败行为，保证最小错误信息可返回。
- 报告拥有所需文本和上下文，交付后可以独立于 Host、Diagnostics 和原始 Plugin 存活；其存储和析构机制同样不能依赖已销毁的 Host 分配域或已卸载代码。不得保留借用字符串、插件格式化回调或依赖其字典才能阅读的内容。代码身份不可识别时，保留数值表示。
- 回滚、释放等次要错误追加到报告，不能覆盖触发操作失败的主错误；若清理失败使必要不变量无法保持，转入 Check/Fatal，不再宣称可以安全返回普通失败。
- 异步子任务分别收集有界报告，在完成或排空后由父操作归并。父操作必须约束子报告的总存储预算，不能用无限创建子报告绕过有界要求；容量耗尽使用截断语义。
- 取消请求不销毁仍被任务访问的报告存储；任务、上下文和报告遵守同一操作生命周期。异步迁移显式转移或复制上下文，不依赖 TLS，也不强制子任务并发写同一报告。
- 父操作负责选择主错误。由其他失败引发的取消不能覆盖原始失败；多个独立失败按操作声明的规则选择并归并，不承诺跨线程“物理时间最早者”。需要可重复结果的工具应采用稳定子操作顺序或明确优先级。

失败报告本身不承诺持久保存；调用方展示或写入报告是后续操作，其失败需单独处理，不能改变原操作的 Result。

## 6. Assert、Check 与 Fatal

以下名称是接口方向，最终宏和函数签名尚未冻结：

| 入口 | Debug / Development | Shipping | 使用范围 |
| --- | --- | --- | --- |
| `PG_ASSERT(condition)` | 求值一次；失败进入 Fatal，可在调试器下先中断 | 可完全移除，不求值 | 仅辅助诊断；移除后仍满足正确性与安全性 |
| `PG_CHECK(condition)` | 求值一次；失败进入 Fatal | 同样保留 | 继续执行会破坏必要不变量的检查 |
| `Fatal(...)` | 不返回，最小报告后终止 | 同样保留 | 已确认不能安全继续的状态 |
| `LogError(...)` | 记录事件，正常返回 | 受日志策略控制 | 不代替错误返回或 Fatal |

- Assert/Check 条件不应包含业务副作用；消息构造必须延迟到失败分支。被禁用的 Assert 不得承担资源获取、输入校验或必要状态更新。
- 外部输入的非法值应显式返回错误，不能仅依赖 Assert，也不应普遍把输入错误升级为 Check/Fatal。
- 活跃 Assert/Check 失败后，调试器“继续”也必须走终止路径，不能以处理回调返回值允许带着失效不变量继续运行。
- 此处允许少量宏负责表达式捕获、调用点和条件编译；不改变反射声明禁用标记宏的约束。
- v1 不增加“失败后默认继续”的通用 Ensure；确实可恢复的检查写成显式分支和 Result。
- Fatal 是进程级终止。需要正常停止某个 World、Context 或 Host 时，使用其关闭协议，不用 Fatal 模拟局部恢复。

## 7. 三条独立的处理路径

```text
可恢复失败 -> Error / Result -> 调用方处理、传播或正常回滚
                                  |
                                  +-> 重要操作交付有界失败报告
                                  +-> 在处置边界按需记录普通日志

普通日志 -> 过滤 -> 生成拥有型有界记录 -> Host 诊断路由 -> Sink

Fatal / 致命 OOM -> 常驻的最小应急路径 -> 平台终止
```

Error/Result 不依赖 Diagnostics。最小应急路径只依赖常驻 Foundation 代码和经过验证的少量平台原语，不依赖 EngineHost、ServiceRegistry、VFS、TaskScheduler、PanguMeta 或引擎 Allocator。

普通 Diagnostics 由明确的 EngineHost 实例配置并拥有，可以作为强类型持有的 Concrete Service；Context/World 通过明确依赖使用它，并携带所属作用域的值标签。每个实例具有固定的日志资源预算，运行时不自动扩容，不争用隐式进程全局队列，也不依赖全局“当前 Host”。这只冻结所有权和接口边界，不承诺 v1 已支持多个 Host 同时运行；多 Host 生命周期留给 EngineHost 专项规范。上述划分不要求新增三个 Pangu Module，也不引入第四种 Service Scope。

## 8. 普通诊断与日志

### 8.1 记录与过滤

普通日志采用 Trace / Debug / Info / Warning / Error 等级。Fatal 使用独立终止入口，不作为可被级别过滤丢弃的普通日志。

记录可以包含级别、分类、消息文本、结构化 Error、Scope/操作关联值、时间和线程信息、报告源位置。可选字段不可用时必须明确缺失，不能为了补齐字段再依赖尚未启动的 Service。

- 默认路径使用预先确定容量的记录/缓冲区；文本、字段数及上下文长度有上限。超长时保留 Error 数值身份并标记截断，不自动转为无界堆分配。
- 编译期和运行期过滤应在格式化与昂贵参数计算之前发生；普通函数的急切参数求值不能被宣传为“禁用后零成本”。实现需采用调用点条件或惰性参数机制。
- 生产者在调用返回前完成格式化或必要的数据复制；入队记录不能保留栈对象、资源借用、用户格式化回调、`format_args` 或 Plugin 静态文本指针。
- 默认生产者路径只接受能有界写入的值和文本视图；支持任意用户类型的昂贵格式化须显式选择并说明分配成本。格式化失败降级为最小记录，不能覆盖业务错误。
- 日志参数不得承担业务副作用。调用方不得依靠记录成功决定业务操作是否成功；要求可靠审计的数据应有独立、可失败的持久化接口。

### 8.2 队列、Sink 与失败

默认实时业务日志通过有界异步提交，不在业务线程执行可能阻塞的 Sink I/O。工具、启动诊断等场景可以显式选择同步输出，并声明阻塞行为；同步和异步路径都必须满足相同的数据所有权约束。

默认业务日志提交不等待队列空间，也不通过运行时扩容解决背压。Warning/Error 应优先于低级别记录保留，可采用预留容量或优先丢弃低级别记录；具体算法尚未冻结。容量仍不足时允许丢弃，包括 Error 级别，但 MUST 累计可查询的丢弃统计，统计不能递归写日志。普通日志不承诺可靠送达；重要失败仍通过 Result 与独立报告交付，需要立即报告的严重状态可以尝试应急摘要，Fatal 则始终走独立路径。

Sink 的 I/O 失败不改变原业务 Result。失败 Sink 应能被隔离/停用，其错误通过状态、计数或最小应急摘要表达，不递归调用自身。普通 Sink 的阻塞预算须由实现声明；禁止在持有 Registry/路由内部锁时调用未知 Sink 代码。

实现必须说明存留记录的处理次序，以及优先保留策略对丢弃的影响；多个生产线程不承诺真实事件的全序。被优先策略移除的已接受记录同样计入丢弃统计，不能视为成功写出。

Flush 在调用时确定本次覆盖的已接受记录范围，等待这些记录完成约定的 Sink 处理，并报告该范围中的丢弃或 Sink 失败；不等待之后继续产生的新日志。范围内的记录可以已经处理、仍在队列或已被丢弃，实现不得遗漏其结果。具体范围标识与统计算法未冻结。队列接受前被丢弃的日志通过累计统计保持可见，不能因不属于 Flush 范围而被隐瞒。

Flush 的完成状态与数据是否完整必须区分，不能只用一个成功标志掩盖丢弃或 I/O 失败。默认 Flush 不承诺持久落盘；需要该保证的调用方使用单独声明的持久化能力。

### 8.3 源位置与 Module 边界

`std::source_location` 可用于调用点采集，但它的文件名和函数名访问器返回字符指针。持久化或异步记录必须复制所需文本，或转换为由诊断设施安全持有的稳定标识；不能假定 Module 卸载后这些指针仍有效。标准接口见 [source_location observers](https://eel.is/c++draft/support.srcloc.obs)，实际行为需按 C++23 工具链验证。

v1 支持由宿主配置的文件、终端、调试输出、测试收集端及其他常驻 Sink 扩展；Sink 实现代码必须在所属 Diagnostics 的整个生命周期内驻留。Plugin 可以产生日志，但可独立卸载的 Plugin Sink 延后设计，不将其动态注册/撤销协议纳入 v1。

Sink 停用与销毁仍须先阻止新调用、等待在途调用结束，在代码有效时销毁状态；必要的 CodePin 不能提前释放。排队记录应已拥有其内容，不能依赖原日志生产者 Plugin 的格式化代码。

Host 诊断实例销毁后，调用方不能继续使用裸指针或失效引用。路由关闭必须与调用方生命周期同步；合法的晚期诊断只能使用仍有效的最小应急入口。

## 9. 启动与关闭

| 阶段 | 允许的能力 | 约束 |
| --- | --- | --- |
| Bootstrap | Error/Result、Check/Fatal、最小应急输出 | 不做延迟初始化的堆分配，不要求日志配置或文件系统就绪 |
| Diagnostics 初始化 | 显式配置、缓冲分配、Sink 创建 | 初始化显式支持可恢复 OOM；失败时默认降级，必需能力失败则正常回滚启动 |
| Running | 默认有界异步日志，显式选择的同步输出 | Host 拥有固定预算，队列和 Sink 有明确线程协议 |
| Quiescing / Draining | 清理中的诊断、排空已接受记录、停用 Sink | 先停业务工作；保留清理仍需的诊断能力和代码驻留 |
| Diagnostics 已关闭 | 最小应急输出、Check/Fatal | 不再访问已经销毁的 Host 日志对象 |

Diagnostics 初始化是明确支持可恢复 OOM 的接口。其缓冲、队列及必需初始化步骤不得依赖隐式的致命分配；失败时释放部分状态、返回失败并保留应急能力。普通日志无法初始化时，Host 默认降级到应急诊断并继续启动；若工具或运行模式显式声明某项报告保存能力是必需启动条件，该能力失败应返回启动失败并正常回滚，而非直接 Fatal。初始化失败的诊断实例不发布为 Ready。

正常关闭时，先停止相关业务生产者并完成其清理；然后关闭普通日志入口，等待正在提交的记录，确定最终排空范围。默认排空已接受记录后再停用并销毁 Sink、释放缓冲。超时、Sink 失败或主动丢弃都必须通过 Flush/Stop 结果明确报告，运行期间的累计丢弃统计也须保持可查询直至调用方取得关闭结果；不能悄悄丢弃后报告完整成功。

诊断消费者若使用执行线程/资源，必须活到其排空完成；不能先关闭它依赖的 Scheduler 再等待日志排空。具体采用专用线程或其他执行资源由实现决定。

Flush/Stop 超时或存在在途 Sink 调用时，应返回未完成状态并保留相关对象及 CodePin；不得为了声称停机完成而强制销毁仍被调用的状态。无法安全完成正常关闭时，是否升级为进程 Fatal 由 Host 的明确策略决定。

最小应急设施及其底层输出能力必须存活到普通引擎清理之后；它不使用插件 Sink。

## 10. 致命错误、OOM 与应急路径

Fatal 路径 MUST 标记为不返回，且不能以异常、`longjmp` 或用户回调恢复运行。终止不是正常 Host Shutdown；不承诺执行析构、Flush 文件、回收 GPU 或保存业务状态。

最小应急路径的契约：

1. 不分配堆内存，不调用普通格式化器、符号解析器或插件代码，不取得可能已由失败线程持有的业务/日志锁。
2. 使用固定上限的内联或栈上数据，优先输出致命原因、数值错误身份及可安全取得的位置；信息不足时输出固定摘要。
3. 重入或多线程同时 Fatal 时，不能等待其他失败线程完成诊断；使用已验证的无分配防重入机制，后续失败直接进入最小终止路径。
4. 对平台输出采用尽力而为策略，不承诺可靠落盘。只有能满足所需非阻塞/有界行为的后端才能进入此路径；不能因为等待终端、管道、文件或普通日志 Flush 而无限推迟终止。
5. 在普通线程上下文提供的 Fatal 能力，不自动等于 POSIX signal、SEH 或进程已损坏状态下可安全使用；这些入口需要独立的平台验证，可进一步退化为更小的崩溃处理路径。
6. 测试通过子进程观察终止，不通过让 Fatal 返回来模拟成功。

OOM 沿用 Memory v1：原生 Try 路径返回失败；失败即终止的分配及 PMR 适配进入 Fatal。声明可恢复 OOM 的链路，其错误构造、传播及回滚也必须能在无额外分配下完成。普通 Result 不自动提供此保证；底层使用 Try 分配器，不代表上层 STL 容器自动具备可恢复 OOM。Diagnostics 初始化必须满足可恢复 OOM 契约，其他接口按各自声明执行。

第三方或标准库自行终止，不保证经过引擎的 Fatal 入口；适配时必须记录其行为。可用的 terminate/崩溃钩子只作尽力补充，不能宣传为覆盖所有失败源。

## 11. 与 ABI、工具及现有规范的关系

- Result/expected 是受控 C++ 边界类型，不是稳定 C ABI 或持久化格式。C ABI 应显式定义数值状态、输出参数和所有权；具体布局由边界规范决定。
- Error 值及已交付的操作级失败报告可独立于原始 Plugin 存活，不代表任意成功值、其他领域对象或 Sink 也无需 CodePin；各自遵守 Memory/Module 契约。
- CLI 工具在入口将最终失败映射为约定的退出码；不得直接截断任意域的 Code 作为进程退出码。
- 普通诊断支持测试注入收集端；Error 核心测试无需启动 EngineHost、线程或文件系统。
- Shipping 可以去除 Assert、详细源路径、Trace 和调用栈等可选诊断；Result 处理、必要 Check、Fatal、所有权和同步规则不能随之消失。

## 12. 验证与验收

以下是后续实现的验收项，本次文档设计不宣称已经通过：

| 场景 | 必须验证的结果 |
| --- | --- |
| 无额外堆内存可用 | Error 创建/复制/传播成功；可恢复回滚不另触发 OOM |
| Diagnostics 初始化中的分配或 Sink 创建失败 | 部分状态清理，实例不发布 Ready；默认降级，显式必需能力失败则回滚启动 |
| Result 成功、失败及 void | 分支与载荷正确；忽略结果有诊断；无异常配置不依赖 `value()` |
| 原始系统调用失败后再记日志 | 保留的是原始错误值，不是日志操作覆盖后的错误 |
| 未知 Error Domain / 插件卸载 | 可传播并输出数值；无悬空字符串、类别对象或格式化回调 |
| 启动失败、回滚、关闭后的诊断 | 应急路径可用；未访问未初始化或已销毁的 Service |
| Debug / Development / Shipping | Assert 开关不改变业务状态；Check/Fatal 在所有配置下有效 |
| 队列满、文本超长、格式化失败 | 优先保留 Warning/Error；有界丢弃/截断且可观察；业务结果不被日志失败改变 |
| 慢速 Sink 与固定日志预算 | 默认业务线程不执行阻塞 Sink I/O，不等待队列空间，不运行时扩容 |
| Sink 重入、失败及并发停用 | 无递归日志风暴；实现代码在 Diagnostics 生命周期内驻留，在途调用完成前不释放状态和 CodePin |
| Drain/Flush 超时 | 明确未完成；不伪造成功，不强制释放仍使用中的资源 |
| Flush 期间持续产生日志及已有记录被丢弃 | 本次范围不扩张；报告范围内的丢弃/Sink 失败，累计拒收统计仍可查询，不宣称持久落盘 |
| Fatal / 致命 OOM / 并发 Fatal | 子进程终止；不依赖堆分配、普通日志锁或无限等待 |
| 异步上下文与源位置 | 记录持有数据；来源和报告位置区分明确 |
| 主错误后的回滚失败与报告截断 | 主错误及其现场优先保留，次要错误不覆盖主错误；状态已不安全时进入 Check/Fatal |
| 并发子任务失败与取消 | 子报告总预算有界，排空后归并；取消不提前释放存储，不覆盖原始失败；主错误按声明规则选取 |
| Host 关闭及生产者 Plugin 卸载后读取失败报告 | 报告自持文本和上下文，不查询已销毁字典或调用插件代码 |
| 五平台工具链 | 分别验证无异常 expected 使用、应急输出及终止入口；移动端编译不能代替运行验收 |

临时验证放在 `.probe/`；确认稳定的回归用例再纳入正式 `Tests/`。性能验证至少覆盖成功路径、错误传播、禁用日志、普通记录构建及高并发丢弃路径。

## 13. 冻结范围与后续设计

已冻结：错误分类与默认无堆分配 Error；采用 `std::expected` 的公共结果表达、显式传播及 OOM 保证边界；操作级有界失败报告及异步归并；Assert/Check/Fatal 区别；Host 所有的固定诊断预算、默认有界异步提交、Warning/Error 优先保留和显式丢弃统计；初始化可恢复 OOM 与降级；v1 Sink 代码驻留；正常关闭与 Flush 范围/完成语义；独立应急终止路径。

未冻结：Error Domain ID 编码与发放、Native Code 布局、公共头文件/名称/函数签名、报告与记录容量、过滤配置、优先保留/队列/Sink 同步及 Flush 统计算法、各平台终止/崩溃原语，以及具体 CMake Target 归属。这些事项不能由示意代码或本文标题推定已冻结。

v1 不承诺可独立卸载的 Plugin Sink 或多个 Host 同时运行；若后续引入，须在相应专项规范中明确生命周期和兼容性。本文件的设计冻结不替代第 12 节的实现验收。
